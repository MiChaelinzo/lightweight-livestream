# Top 100 improvements

Ranked list of 100 improvements for LightStream. It is a prioritization aid built from one author's judgment, not a measurement. Status and evidence come from the code, [ROADMAP.md](../ROADMAP.md) and [EVIDENCE.md](EVIDENCE.md). Context: [AUDIT.md](AUDIT.md), [BLUEPRINT.md](../architecture/BLUEPRINT.md), [DELIVERY.md](../architecture/DELIVERY.md). Index: [docs/README.md](../README.md).

Count by status: 30 Done, 7 Partial, 63 Roadmap. Most of the list is future work, so read the Status column before quoting any row as a feature.

## How scores work

Each item gets six scores from 1 to 5. They are judgment scores with no measured basis, so treat differences of a few points as ties.

| Column | 1 means | 5 means |
|---|---|---|
| User impact | few people notice | most streamers on weak PCs feel it |
| Effort (ease) | months of work, or needs hardware that is not available here | hours to a day, testable in this repo |
| Innovation | nearly every streaming tool has it | uncommon in OBS class tools |
| Perf gain | no CPU, RAM or stability change | large expected CPU, RAM or dropped frame reduction |
| Commercial | no effect on adoption or trust | removes a blocker for real users |
| Judge appeal | invisible in a demo | easy to show and explain in two minutes |

Effort is scored as ease, so a high number means cheap. Weighting formula (maximum 50, all fives):

`total = 3*impact + 2*effort_ease + 1*innovation + 2*perf + 1*commercial + 1*judge`

The weights favor user impact on low-end PCs, then cheap and performance-relevant work. They are a choice, not a law. Ties are broken by user impact, then by the order the item was written. Totals were computed by a throwaway script, not by hand.

Status values: **Done** (implemented and unit tested), **Partial** (some of it exists), **Roadmap** (not started; design only, no code). A Done row does not mean verified on real hardware; the README verification table lists what was never run on a real PC. Perf gain is an expectation, not a measurement, except where [EVIDENCE.md](EVIDENCE.md) or [BENCHMARKS.md](../BENCHMARKS.md) gives numbers.

## Hackathon mode (Phase 19)

### What to show, in order (about 5 minutes)

All commands run from the repo root without installing anything: `export PYTHONPATH=src` then `python3 -m lightstream ...`. FFmpeg must be on PATH for steps that need it. Rehearse once; none of this was recorded as a video here.

1. **Zero install, tiny footprint** (30 s). `python3 -X importtime -c "import lightstream.cli" 2>&1 | tail -1`. Measured here: about 52 ms import and 22.7 MB RSS ([EVIDENCE.md](EVIDENCE.md) section 2). Say the machine was a Linux sandbox, not a low-end laptop.
2. **Honest readiness** (45 s). `python3 -m lightstream readiness --ffmpeg <path>`. Shows a 0 to 100 score with named factors and says which ones were not measured.
3. **Safe command preview** (45 s). `python3 -m lightstream start --platform facebook --profile potato --dry-run`. The key is replaced by `****`. Point out `-threads 2` and `-filter_threads 2` (Gaming First thread cap; CPU affinity is applied to the process, not shown in argv). If the key prompt appears, set `STREAM_KEY=demo` first.
4. **Bench harness** (60 s). `python3 -m lightstream bench --ffmpeg <path> --seconds 5 --out /tmp/bench.json`. Each metric is labeled measured or unavailable.
5. **Auto-scale story** (60 s). Show `docs/ARCHITECTURE-NOTES.md`: three alternatives evaluated, one chosen and why. Run `python3 -m unittest tests.test_autoscale` to show the hysteresis tests.
6. **Web calculator** (30 s). Open the deployed site only if the Vercel deploy was checked; otherwise `python3 -m http.server -d web`. It never asks for a key.
7. **Close with the verification table** (30 s). Open the README "Verification status" section and the UNVERIFIED rows. Honesty about limits is the differentiator.

### Judge talking points (each tied to a real design fact)

- One FFmpeg process does capture, scale, encode and tee to a local recording. No second relay process, so no extra CPU or RAM ([ARCHITECTURE-NOTES.md](../ARCHITECTURE-NOTES.md)).
- The Python process measured 22.7 MB RSS and has no third-party dependency. Compare the target of 300 MB in [BLUEPRINT.md](../architecture/BLUEPRINT.md#2-performance-memory-cpu-and-gpu-budgets).
- Quality changes only happen when the user opted in (`--auto-scale`), and each change says why.
- 452 unit tests plus 25 node tests pass, and the docs mark every claim VERIFIED, PARTIALLY VERIFIED or UNVERIFIED.

### Honest limitations to say out loud

- No real go-live to Twitch, YouTube or Facebook was run in the dev environment.
- No Windows, macOS, GPU encoder or tkinter window was run. GUI layout is drawn from code, not screenshots.
- No game FPS impact was measured. Gaming First is a design, not a proven gain.
- No OBS, Streamlabs or XSplit number exists in this repo. See the methodology in [DELIVERY.md](../architecture/DELIVERY.md#competitive-benchmark-methodology).
- Emergency mode, backup endpoints, plugins, mobile remote and VP9 or AV1 output are Roadmap.
